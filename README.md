# social-video-editor (`sve`)

[![tests](https://github.com/MetadHInd/social-video-editor/actions/workflows/tests.yml/badge.svg)](https://github.com/MetadHInd/social-video-editor/actions/workflows/tests.yml)

A Python + FFmpeg engine that turns raw phone clips into finished **vertical social videos**
(TikTok, Reels, Shorts). It analyzes your footage, proposes an editable plan, and renders it:
a hook in the first second, cuts that land on the music's beat, typed text cards with color emoji,
polaroid and collage pieces, ASMR-friendly audio, loudness mastering (targets −14 LUFS) and correct handling of
iPhone HDR footage.

Everything the engine decides is written to a plain `plan.json` that you (or an AI agent) can edit
and render again. Originals are never modified.

## Features

- **Analysis** — brightness, sharpness, motion and color per frame (OpenCV), scene changes
  (PySceneDetect), loudness and sound peaks (librosa), word-level transcription (faster-whisper).
- **Automatic first plan** — scores every instant (motion, loudness, peaks, voice, keywords,
  sharpness, color), picks the best windows without cutting phrases or crossing scene changes,
  covers the whole footage, and starts with a *teaser* hook (the best moment first).
- **Beat-synced editing** — music beat grid and "drop" detection; the song can start so its drop
  lands at a chosen second; cuts snap to the nearest beat, or every cut lands exactly on a beat
  (`"beats": N` per shot); `beat_pulse` zooms on every beat.
- **Animated graphics from data** — bars, big numbers, product cards, titles, headlines, lists and
  step-by-step diagrams with illustrations (phone, router, server, chip…), written as a few
  key/value pairs and drawn locally: laid out for vertical or landscape, alive (scenery, blinking
  lights, a marker that travels), themeable per channel with packs. See [docs/GRAPHICS.md](docs/GRAPHICS.md).
- **From a script to the video** — write what you say with cues for what is on screen
  (`[bars data="…"]`), record yourself repeating whatever goes wrong, and the `explainer` recipe finds
  the best take of every sentence, puts them in script order and shows each graphic or photo over your
  voice, with subtitles that say what the script says. While the presenter is on screen, small
  illustrated notes pop up around them as things are named, and cuts and long shots rotate three
  framings and drift slowly, so one camera reads like several. Optionally the presenter stays in a
  corner window (picture-in-picture) over the graphics.
  See [docs/PLAN_FORMAT.md](docs/PLAN_FORMAT.md#scripts-and-cutaways-the-explainer-recipe).
- **B-roll with a paper trail** — a `[broll query="…"]` cue becomes a clip fetched from sources you
  allow: free stock libraries (Pexels, Pixabay), Wikimedia Commons (open licenses only) and the official
  channels of the brands you list (never anyone else's). The local vision model picks the clip and
  the piece of it that show the query best; every file is recorded (`footage/credits.json`: source,
  author, license, hash) and credited on screen and in `credits.txt`; `sve check` warns about clips that
  stay too long or have no record. Clips with printed text are avoided and every clip is framed by
  where its subject is. A **director** cuts to footage wherever the presenter would stay alone on camera
  too long; clips must show what is said and look alive, and when none does the engine **draws the
  moment** instead (an animated scene, a figure, a list). See [docs/PLAN_FORMAT.md](docs/PLAN_FORMAT.md#third-party-footage-sve-broll).
- **Pieces** — video shots (speed ramps, freeze frames, zoom punch, push-in/pull-out, shake, flash),
  **polaroid** shots (last frame of a shot dropped in as an instant photo with a shutter sound),
  **collage** shots (frames of several shots popping in on the beat), and groups of shots.
- **13 transitions** — cut, fade, fade_black, flash, zoom, whip, slide_up, slide_left, circle, pixel,
  blur, radial, curtain (each with its own sound effect where it makes sense).
- **Text** — word-by-word auto subtitles with the active word highlighted; styled text cards
  (hook, label, card, counter, price, cta, simple) that pop in or are typed letter by letter with a
  soft keystroke sound; a card can have a hand-written-style description typed below its title;
  color emoji inside any text.
- **Audio** — denoise, high-pass, voice EQ, compression, extra gain for non-speech (ASMR) moments,
  an optional ASMR mode, music ducking under the voice (or under the ASMR sounds), sound effects
  (whoosh, pop, flash, keystroke, shutter — synthesized if you don't provide your own) and
  mastering that targets −14 LUFS integrated / −1 dBTP (EBU R128 measurement, capped gain +
  oversampled true-peak limiter, true peak re-verified after AAC; a warning in `summary.json` if it
  cannot get there); `sve check` verifies the result with the same measurement.
- **Color** — iPhone HLG HDR → SDR (BT.709) via a generated 3D LUT, automatic levels, white
  balance and brightness matching across shots, optional creative `.cube` LUT and vignette.
- **Export** — 1080×1920 H.264 High / yuv420p / BT.709 + AAC 48 kHz, CRF 17 with a 20 Mbps cap,
  `+faststart`; platform profiles; `.srt` subtitles; a cover image; `plan_used.json`,
  `config_used.json` and `summary.json` next to every version. Unchanged shots are cached and not
  re-encoded.
- **Versions** — every render goes to a new folder (`v1`, `v2`…); variants keep the number of the
  latest version (`v3SinMusica` / `v3NoMusic`, `v3Borrador` / `v3Draft`, `v3Youtube`…).
- **Pauses in speech** — `sve plan` shortens long pauses inside every shot with voice (breaths
  are kept) and joins them with a near-invisible 0.12 s crossfade.
- **Recipes** — layered YAML defaults per video type (unboxing, tutorial, review, vlog,
  before/after, storytime, slideshow, talk) that a project can override.
- **Cheap project overview** — `sve report` prints one screen (or JSON) with everything an editor
  or an AI agent needs to know about a project.
- **Product recognition (optional)** — a local CLIP model finds the products shown in the footage
  (`sve products`), picks windows from a text description (`search.text`) and proposes one shot
  per product in unboxing plans.

## Requirements

- **Python ≥ 3.11**
- **FFmpeg 7 or newer** (with `ffprobe`) on the `PATH` — the engine passes filter graphs with the
  `-/filter_complex <file>` syntax introduced in FFmpeg 7. On macOS: `brew install ffmpeg`; on
  Debian 13 / Ubuntu 25.04 or newer: `apt install ffmpeg`. FFmpeg 7.0 – 8.0 can deadlock when a
  shot's source is decoded with many threads, so on those versions shots decode with 2 threads
  (8.1 and newer use FFmpeg's default); `SVE_DECODER_THREADS=N` sets the count (`auto` = FFmpeg's
  default).
- **Fonts** are looked up by file name (no extension): on macOS in `~/Library/Fonts`,
  `/Library/Fonts`, `/System/Library/Fonts/Supplemental` and `/System/Library/Fonts`; on Linux in
  `~/.local/share/fonts`, `~/.fonts`, `/usr/local/share/fonts` and `/usr/share/fonts`; on Windows in
  `%WINDIR%\Fonts` and `%LOCALAPPDATA%\Microsoft\Windows\Fonts` (sub-folders included, names
  case-insensitive). The default styles use [Inter / Inter Display](https://rsms.me/inter/) (macOS: install
  the `.otf`/`.ttf` files; Debian/Ubuntu: `fonts-inter`) and *Bradley Hand Bold* (ships with macOS).
  A missing font falls back to an installed bold sans-serif (Arial Black, Inter, Segoe UI, DejaVu
  Sans, Noto Sans, Liberation Sans).
- **Color emoji** are drawn with *Apple Color Emoji* on macOS, *Noto Color Emoji* on Linux
  (`fonts-noto-color-emoji`) and *Segoe UI Emoji* on Windows; without an emoji font, or when Pillow
  cannot draw it in color, they are left out.
- **Optional:** [Rubber Band](https://breakfastquay.com/rubberband/) (`rubberband` on the `PATH`;
  `brew install rubberband` / `apt install rubberband-cli`; on Windows the command-line build from
  the Rubber Band site, added to the `PATH`) for AutoMix tempo matching; FFmpeg `atempo` is used
  without it.
- **Hardware acceleration** (analysis proxies and drafts only; the final export always uses
  libx264): VideoToolbox on macOS, NVENC, VAAPI or Quick Sync on Linux and NVENC or Quick Sync on
  Windows, picked automatically after a one-frame test encode, with fallback to software.
  `SVE_HWACCEL=0` forces software; `SVE_HWACCEL=nvenc|vaapi|qsv|videotoolbox` picks one
  (`SVE_VAAPI_DEVICE` sets the VAAPI device). Only VideoToolbox decodes final-quality shots.
  NVENC, VAAPI and Quick Sync are tested with mocked FFmpeg output only (no GPU in CI).
- **Linux:** CI runs the whole suite on Debian 13 (FFmpeg 7.1), and the [Docker image](#docker)
  ships everything above. OpenCV needs `libgl1` and `libglib2.0-0`.
- **Windows 10 / 11:** install Python 3.11+ and FFmpeg 7 or newer (`winget install --id Gyan.FFmpeg
  -e`, `choco install ffmpeg` or `scoop install ffmpeg`; open a new terminal and check
  `ffmpeg -version`), then `pip install -e .` as below. Caches go to
  `%LOCALAPPDATA%\social_video_editor` (`XDG_CACHE_HOME` wins when set). CI runs the whole suite on
  `windows-latest` (FFmpeg 8.1, no GPU, Rubber Band not installed).
- **Speed:** video and photo shots render in parallel (`render.jobs`, default `auto` = half the
  CPUs, 1–3: 17 % faster than one at a time in the benchmark; `SVE_JOBS=1` renders one at a time),
  and numba's compiled librosa code is cached in the user cache folder (`NUMBA_CACHE_DIR`): the first song analysis of a new process took 13 s
  without it and ~3 s with it (measured on 4 cores). `python scripts/bench.py` measures render
  speed on synthetic 4K footage.

## Install

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e .              # the engine and the `sve` command
pip install -e ".[music]"     # + yt-dlp, for `sve music`
pip install -e ".[vision]"    # + sentence-transformers: local CLIP product recognition (optional)
pip install -e ".[graphics]"  # + skia-python: animated graphics (optional)
pip install -e ".[dev]"       # + pytest and ruff
```

The same CLI is available as `sve`, `social-video-editor` and `python -m social_video_editor`.

## Quick start

The **workspace** is the folder given by `$SVE_WORKSPACE` (or the current folder):

```
workspace/
├── projects/            one folder per video (created by `sve new`)
│   └── my_video/
│       ├── project.yaml     name, recipe, sources (in story order), settings
│       ├── plan.json        the editable edit plan (`sve plan`)
│       ├── cache/           probes, analyses, proxies, rendered shots, contact sheets
│       ├── v1/  v2/ …       one folder per render: video, .srt, cover, plan_used.json, summary.json…
│       └── v2SinMusica/ …   variants of the latest version
├── music/               tracks (the first one is used unless a project picks another)
├── recipes/             your own recipes (override the packaged ones with the same name)
└── sfx/                 optional sound effects (whoosh.wav, pop.wav…); generated when missing
```

Spanish names written by earlier versions are accepted too: `proyectos/`, `musica/`, `recetas/`,
`proyecto.yaml` (and Spanish keys inside the files — see [docs/LEGACY_KEYS.md](docs/LEGACY_KEYS.md)).

```bash
export SVE_WORKSPACE=~/videos
sve new my_video --recipe unboxing --sources ~/clips/a.mov ~/clips/b.mov
sve build my_video            # analyze + contact sheets + plan (if missing) + render v1
sve report my_video           # one-screen overview
# edit projects/my_video/plan.json (or project.yaml settings), then:
sve render my_video           # → v2
sve render my_video --no-music   # → v2SinMusica (same beat-aligned cuts, no song)
```

`sve report` is the cheapest way to understand a project. Example (synthetic project):

```
PROJECT demo · recipe unboxing · language es
SOURCES 2 · 08:14.50 total
  0 clip_a.mov 08:02.00 HDR | 1 clip_b.mov 00:12.50 mute
PLAN 5 shots · ~8.5 s before beat alignment · 1 group · 3 texts (hook 1, card 1, cta 1)
  0 hook s1 4.3-6.5 2.2s +zoom_punch | 1 opening s0 9.9-12.3 2.5s /flash | 2 s0 ?100-130 x2 0.7s
  3 polaroid<2 1.2s | 4 collage<0,1,2 2.4s /zoom
  first text: Was it worth it? 👀
MUSIC Some Song.mp3 · start_at auto (rendered from 18.73 s) · 120.0 BPM · tempo_factor 1.5
VERSIONS v1 v2 v2SinMusica v10_failed · latest v2
  v2           demo.mp4 · 21.4 s · 5 shots · -14.05 LUFS · +srt · check.json · listen/ 1 files
  v2SinMusica  demo_sin_musica.mp4 · 21.4 s · 5 shots · -14.05 LUFS · +srt
PRODUCTS 2 segments (test-model, es)
  earrings s0 12.0-15.5 c0.71 | necklace s0 30.0-33.0 c0.31?
  ⚠ 1 low confidence (<0.5, marked ?): look at those images (sve thumbs <project> --source S --start A --end B)

  ...
```

Shot tokens read `index role source start-end [xspeed] duration [/transition] [+effects]`;
`?a-b` is a `search` window resolved at render time; `polaroid<k` / `collage<i,j` name the shots
they are drawn from.

## Recipes

Defaults live in [`recipes/base.yaml`](src/social_video_editor/recipes/base.yaml) (every key is
commented). Each recipe only overrides what it changes; a project overrides the recipe in
`project.yaml → settings` (deep merge: `base → recipe → settings`).

| Recipe | Formula |
|---|---|
| `base` | Generic defaults: 30 s target, teaser hook, 0.8–3.2 s shots. |
| `unboxing` | Hook with the result → opening with ASMR sounds → reveal with zoom → reaction / price → loop ending. |
| `haul` | Calm "aesthetic" unboxing: package opening → every product at real speed with plain cuts, one title at the start and a soft call to action at the end, steady music over the ASMR sounds. |
| `tutorial` | Final result first → short numbered steps (waiting sped up) → result again; progress bar. |
| `review` | Verdict or question → the good → the bad → verdict + question to the audience. |
| `vlog` | Most striking moment → fast chronological sequence on the beat → emotional/funny ending. |
| `before_after` | The "after" in 1 s → "before" → sped-up process → reveal with flash/zoom. |
| `storytime` | Strongest line first → story without silences, big subtitles, almost no effects. |
| `explainer` | A presenter talking to the camera from a script (`script.md`): the best take of every sentence in script order, long pauses shortened, punch-ins at the jump cuts, and the script's cues (graphics, photos) shown over the voice. Subtitles from the script's own words. |
| `talk` | Meeting, class or screen recording (landscape, long-form): the whole recording in order, only long pauses shortened, joined with a 0.12 s crossfade; neutral look and sound, no music, no texts. |
| `slideshow` | Photo slideshow (landscape): every photo in chronological order, gentle Ken Burns, soft crossfades, warm look, gentle exposure fix, a playlist blended back to back. |

Put `recipes/<name>.yaml` in your workspace to add a recipe or replace a packaged one. The first
line comment is shown by `sve recipes`.

How a configuration is resolved (`YamlRecipeRepository.load`): every file name is looked up first
in `<workspace>/recipes/` (or legacy `recetas/`), then among the packaged recipes, and the **first
file found is used whole — files with the same name are never merged with each other**. Then
`base.yaml` (the first one found) ← `<recipe>.yaml` (the first one found) ← `project.yaml →
settings` are deep-merged in that order. So a workspace `recipes/base.yaml` *replaces* the packaged
base for every recipe, and must therefore be a complete copy of it (a file with only a few keys
would lose every other default).

## The plan (`plan.json`)

Shot times are seconds **inside each source**; text times are seconds of the **final video**
(or relative to a shot). Minimal example:

```json
{
  "shots": [
    {"source": 1, "start": 4.2, "end": 6.4, "role": "hook", "effects": [{"type": "zoom_punch"}]},
    {"source": 0, "start": 9.8, "end": 12.3, "speed": 1.5, "transition": "flash", "beats": 3},
    {"source": 0, "search": {"range": [120, 135], "dur": 1.8, "criterion": "product"}},
    {"type": "polaroid", "from_shot": 2, "beats": 2, "text": "my favorite"},
    {"type": "collage", "from_shots": [0, 1, 2], "beats": 8}
  ],
  "texts": [
    {"text": "Was it worth it? 👀", "shot": 0, "style": "hook"},
    {"text": "Earrings", "description": "pastel colors ✨", "shot": 2, "style": "card"},
    {"text": "Which one is your favorite? 💬", "start": 9.0, "end": 12.0, "style": "cta"}
  ]
}
```

Full reference: [docs/PLAN_FORMAT.md](docs/PLAN_FORMAT.md).

## Product recognition (optional)

A local **CLIP** model (through `sentence-transformers`, CPU by default, nothing leaves your
machine) can recognize the products shown in the footage. It is an **optional extra**:

```bash
pip install -e ".[vision]"
```

The first use downloads the models once (**≈1.2 GB**, to the Hugging Face cache); frame
embeddings are cached per source in `cache/<id>_clip.npy`. Without the extra the engine works as
before. What uses it:

- **`sve products <project>`** — always uses the model (and downloads it if needed): prints a table
  of the product segments (source, start–end, best window, proposed name, confidence, score) and
  writes `cache/products.json`, which `sve report` summarizes. Names come from a packaged list of
  ~80 small products in the project language (`vision.vocabulary` sets your own list).
- **`search.text`** in a shot — `{"source": 0, "search": {"text": "phone case", "range": [40, 60]}}`
  picks the window that best matches the description. It uses the model **whenever it is
  available**; otherwise it falls back to the `product` heuristic with a warning.
- **Unboxing plans** — the `unboxing` recipe sets `vision.product_plan: true`: with the model
  available, `sve plan` proposes one shot per detected product (a card with its proposed name and
  an `n/N` counter; the most confident `vision.stars` products get a fast → slow ramp and a
  polaroid; a collage at the end). Without the model, the regular plan is made. The `haul` recipe
  uses the same plan without cards, counters, ramps, effects or collage (`vision.cards`,
  `counters`, `collage`, `product_effect`, `stars: 0`), plus `hook.text_duration` and `cta.text`.
- **CLIP product criterion (opt-in)** — with `vision.product_search: true`, a `search` with
  `criterion: product` scores frames with the model instead of the sharpness/color heuristic.
  It is off by default because it changes the windows of existing plans.

"Available" follows `vision.enabled`: `auto` (default) = used when installed **and** already
downloaded; `true` = may download it; `false` = never (except `sve products`). All keys:
[docs/PLAN_FORMAT.md](docs/PLAN_FORMAT.md#vision).

## Photo slideshows (landscape)

Still photos are sources too: a source may be a photo or a **folder** (scanned recursively; every
photo becomes a source, ordered by capture time from EXIF). The `slideshow` recipe turns them into
a long 16:9 video: one shot per photo with a gentle Ken Burns motion and soft crossfades, photo
durations spread over the music with the changes on the beat, and a playlist mixed back to back
(AutoMix, beat-matched when the tempos are close).

```yaml
# projects/holidays/project.yaml
name: holidays
recipe: slideshow
sources:
  - /path/to/photo/folder         # every photo inside it (subfolders too)
settings:
  music:
    playlist: [slideshow_songs]   # tracks and/or folders (looked up in the project, then music/)
    automix: {enabled: true}
  photo:
    duration: 4.5                 # seconds per photo (fitted to the music: photo.fit_to_music)
    auto_tone: 0.6                # gentle exposure fix for dark / backlit photos (0 = off)
  color: {warmth: 0.25, vignette: 0.15}
```

```bash
sve enhance holidays                       # optional: upscale small photos, reduce huge ones (cached)
sve plan holidays                          # one "photo" shot per photo, chronological
sve thumbs holidays                        # contact sheets of the photos themselves
sve render holidays --profile landscape    # 1920×1080
sve report holidays                        # photo count, playlist (songs, minutes, AutoMix), summary
```

`photo.auto_tone` lifts underexposed photos with a smooth lightness curve and a little local
contrast, and recovers the shadows of backlit ones locally (subjects in front of a bright window or
sky get brighter, the window or sky does not); blacks and whites stay put, colors keep their hue,
and well-exposed photos are left untouched. Photo segments are cached at `render.photo_crf` (default 16). Long videos are joined in
chunks (`render.chunk_threshold` / `render.chunk_size`). Full keys: [docs/PLAN_FORMAT.md](docs/PLAN_FORMAT.md).

## Language

The default **content language is Spanish** (`language: es`); English (`en`) is the other
supported value. The code, logs, CLI and file keys are always English. The language affects:

- **Transcription** — Whisper's language (`transcription.language: null` follows `language`).
- **Localized defaults** — any recipe value written as `{es: …, en: …}` takes the value for the
  configured language: the keyword lists that boost the scoring (`selection.keywords` in
  `unboxing`, `tutorial`, `review`) and the Whisper context prompt (`transcription.context` in
  `unboxing`). On-screen texts are never generated in a language: you write them in `plan.json`
  (the recipes ship with `hook.text: null`).
- **Version folders and file names** — variants and output files are named in that language:

  | | `es` (default) | `en` |
  |---|---|---|
  | `--no-music` | `v3SinMusica/…_sin_musica.mp4` | `v3NoMusic/…_no_music.mp4` |
  | `--draft` | `v3Borrador/…_borrador.mp4` | `v3Draft/…_draft.mp4` |
  | `--profile square` | `v3Cuadrado/…_cuadrado.mp4` | `v3Square/…_square.mp4` |
  | cover image | `…_portada.jpg` | `…_cover.jpg` |
  | failed render | `v4_fallida/` | `v4_failed/` |

**To change it**, set `language` in a recipe or in the project's settings:

```yaml
# projects/my_video/project.yaml
name: my_video
recipe: unboxing
sources:
  - path: /path/to/clip.mov
settings:
  language: en              # es | en
  transcription:
    language: es            # optional: transcribe Spanish speech while naming files in English
```

Legacy Spanish project files work the same way: `ajustes: {idioma: en}` in `proyecto.yaml`.
To make English the default for **every** project in a workspace, copy the whole packaged
[`recipes/base.yaml`](src/social_video_editor/recipes/base.yaml) to `<workspace>/recipes/base.yaml`
and change its `language: es` line to `language: en`. Every recipe (packaged or yours) is merged on
top of that base, so all of them inherit English unless the recipe itself or a project's
`settings` sets `language`. (Copying only one recipe, e.g. `recipes/unboxing.yaml` with
`language: en`, changes only the projects that use that recipe; a `base.yaml` with nothing but
`language: en` replaces the packaged base and loses every other default — see
[Recipes](#recipes).) Any other value is rejected (`Unknown language`).

## Architecture

Hexagonal (ports and adapters): a pure `domain/`, `ports/` (Protocols), `adapters/` (FFmpeg,
OpenCV, librosa, Whisper, Pillow, files, yt-dlp), `application/` use cases, and `container.py`
wiring them together. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). The research behind the
defaults is summarized in [docs/RESEARCH.md](docs/RESEARCH.md).

## Design decisions

- **Hexagonal core, heavy tools at the edges.** FFmpeg, OpenCV, librosa, Whisper, Pillow and CLIP
  each sit behind a `typing.Protocol` port and are wired in one place (`container.py`). The domain
  (timeline, beat math, shot selection, text layout, AutoMix planning, photo timing, render checks)
  is pure Python, so it is unit-tested without media and an adapter can be swapped without touching
  a use case. Optional extras (CLIP, Real-ESRGAN/torch) are imported lazily, and Whisper runs in a
  subprocess because its PyAV libraries clash with OpenCV's in one process.
- **The video is a Composite of shots.** A `Sequence` holds video shots, still photos, groups and
  *drawn* shots (polaroid, collage) built from other shots' frames. `render_order()` renders
  dependencies first and rejects missing or circular references before anything is encoded;
  rendering is a visitor (`visit_video / visit_polaroid / visit_collage / visit_photo`), so a new
  shot type is a subclass plus one visitor method. Leaves wrap the plan's dicts without copying,
  so beat alignment writes straight into the plan that is saved as `plan_used.json`.
- **One cached segment per shot.** Each shot is encoded on its own, keyed by a hash of everything
  that changes its pixels or sound (shot keys, source identity, output size, relevant config,
  draft flag, segment version). Editing one shot in `plan.json` re-encodes only that shot; the
  final pass joins segments, transitions, the text layer, music and sound effects. Source ids
  include a hash of path, size and mtime, so a replaced file is never served from a stale cache.
- **Chunked compose for long renders.** A slideshow can have hundreds of crossfades, too many for
  one filter graph. Long timelines are joined in chunks; each chunk ends where the transition into
  the next one begins, and the next chunk starts with that same transition, so the chunks meet on
  plain cuts and the final pass reads them sequentially through the concat demuxer. Segment audio
  is trimmed to exactly its picture length so A/V never drifts over many transitions.
- **Beats decide the cuts.** Music analysis fits a regular beat grid to the detected onsets
  (disambiguating half / double tempo) and finds the drop. Cuts either snap to the nearest beat or
  half beat, or — when any shot asks for `"beats": N` — every cut lands exactly on a beat, with the
  middle of each transition on it. Texts can be anchored to shots, so they follow the re-timed cuts.
- **AutoMix as a plan, then a render.** For playlists, `domain/automix.py` decides (without audio
  I/O, from each song's beat grid and level envelope) its in-point, out-point, loudness gain and
  transition: a time-stretched beat-matched blend when tempos are close (also at ×2 / ×½), else a
  short crossfade, both with a bass swap. A beat-matched blend enters on the first strong downbeat
  and leaves at the end of an 8-bar phrase before the outro gets quiet. A short crossfade cannot
  hide a quiet stretch, so it leaves at the last loud phrase end before the outgoing song's energy
  drops and enters on the incoming song's first loud downbeat (quiet intros are skipped). The
  FFmpeg/numpy adapter measures the songs and renders that plan; the one thing it adds is a make-up
  gain on short crossfades that follows the rendered overlap's loudness (BS.1770, in the 1 s
  windows `sve check` uses), so a splice does not dip below the songs around it. Photo durations are
  then fitted to the mix so every photo change is on a beat, song boundaries are photo changes and
  the video ends with the music.
- **Orientation comes from the output size.** Portrait uses the TikTok / Reels safe zone (caption
  area at the bottom, button rail on the right); landscape uses title-safe margins on every side.
  Text sizes scale with the short side, polaroids and collage grids are laid out per orientation,
  and the summary records every drawn text box so `sve check` can flag boxes outside the zone.
  Text is drawn once per visual state as still PNGs (an ffconcat list), not frame by frame.
- **Privacy-first split between engine and workspace.** This repository contains only code,
  recipes and docs. Footage, photos, music and renders live in a separate workspace
  (`$SVE_WORKSPACE`), originals are never modified, `.gitignore` refuses media files (the synthetic
  demo GIFs are the only exception), the vision model runs locally, and generated assets such as
  LUTs go to the user cache, never into the package.
- **Tests on synthetic media only.** Unit tests cover the pure domain; integration tests generate
  their own media with FFmpeg `lavfi` sources, numpy click tracks and Pillow images in a temporary
  workspace, render real files, and assert on what can be measured: durations to the frame,
  loudness after mastering (same BS.1770 measurement as `sve check`), cuts on beats, AutoMix
  splices without dips, safe-zone boxes. Nothing personal is ever needed to run the suite.

## Docker

The image runs `sve` on Linux with everything it needs: Python 3.12, FFmpeg 7, Rubber Band,
OpenCV's system libraries, Inter / Inter Display, fallback fonts and Noto Color Emoji.

```bash
docker build -t sve .
docker run --rm sve --help
docker run --rm -v "$PWD/workspace:/workspace" --user "$(id -u):$(id -g)" sve report my_video
```

The mounted folder is the workspace (`projects/`, `music/`, `sfx/`, `recipes/`); downloaded models
and caches go to `/workspace/.cache`, so they survive between runs. The container runs as an
unprivileged user; `--user` keeps the files it writes owned by you. VideoToolbox is macOS-only, so
the container always decodes in software.

from inside the app instead.
